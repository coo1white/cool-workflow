| 2026-07-13 | An async acquire path for `withFileLock` (`withFileLockAsync`, `src/shell/fs-atomic.ts`) so a long-lived process — the MCP server, `src/mcp/server.ts` — does not freeze its event loop during a contended lock wait | Parked, not rejected — serves no North Star track directly (internal robustness, not pipeline/recovery/manifest) and is a large, higher-risk refactor. The 2026-07-13 perf-audit backoff fix cut the TYPICAL freeze and the frequency of long ones, but the acquire is still synchronous (`Atomics.wait`), so under PERSISTENT contention the calling thread — and the MCP server's whole event loop, including SIGINT/SIGTERM dispatch (`drive.ts:876-893`) — can still block for up to ~6s. The real fix is an async acquire that `await`s a real `setTimeout` instead of `Atomics.wait`, sharing `withFileLock`'s identical acquire/steal/verify body. But it only pays off once the MCP hot paths (`saveCheckpoint`, `withRunStateLock`, trust-audit append, telemetry — all synchronous today, called deep inside the ~197 synchronous tool handlers) go async up their whole call chains: ~20 call sites, and a half-converted chain is exactly where a silent state-corruption or a deadlock would hide — the failure mode the audit flagged. Needs its own `SPEC/state-core.md` pass (the lock protocol is byte-compat pinned), a design, and phased PRs; do NOT bundle it into a mechanical perf fix. Re-entrancy between a sync `withFileLock` and an async `withFileLockAsync` on the SAME target also needs a defined rule (`HELD_LOCKS` is one per-process set today). In fleet operation, where many parallel sessions run together with shared workers, the sync event-loop becomes a product ceiling — the whole control plane's speed is limited by lock contention from one session. This makes the async path a playbook requirement, not just a robustness fix. |
| 2026-09-01 | Bring `schedule`, `routine`, and `sched` into one shape: "CW evaluates, the platform triggers" with CI cron and webhooks as the shared trigger layer | Parked, not rejected — serves no North Star track before a unified design is laid out. The three verbs handle different work today: `schedule` runs loops, cron work, and one-shot reminders (stored in `.cw/schedules/tasks.json`); `routine` runs trigger-based work from API and GitHub webhooks (stored in `.cw/routines/triggers.json`); `sched` runs policy for the run queue (stored in `registry/scheduling-policy.json`). They have shared needs — when to run, what to do if it fails, when to try again — but use separate code and storage. A unified design — "CW evaluates the next action, the platform triggers it" — would let CI cron and webhooks be the one shared layer that fires the work. Before any work starts, needs a North Star track argument (pipeline/recovery/manifest work) and a story of who would benefit. |
